# DeviceTrust 接入与后续约定

本文件记录用户明确要求和当前接入边界。Android 0.3.5 使用 DeviceTrust 0.5.0 基础与安全上报 AAR，使用独立业务应用；发布 APK 的包名与签名保持固定。

## 当前实现

- 应用 ID：`24befb89afb1186d8dc492c722ba302d40b148e8f5ca5a5f`；私有应用密钥保存于 `private/device-trust.json`、服务器环境文件及密钥备份目录，禁止进入 APK、网页和审计正文。
- 新版及升级用户先同意 v2 隐私说明。基础采集关闭 AndroidID；显式执行 ResourceCollector 的硬件资源及指定系统组件元信息采集，不引入定位、RootBeer 或全量应用扫描。
- Rust `/api/risk/prepare` 认证本业务账号并创建一次性挑战，账号、业务类型、IP 与上下文均由服务器确定；SDK 向 DeviceTrust `/v1/secure` 提交 DTP4 加密签名报告。
- `/api/risk/complete` 只接受该账号该事件的有效报告，由 Rust 调用平台评估；后台保存规则证据、策略快照、签名等级、关联设备密钥及上游错误。客户端只得到通用状态与随机参考号。
- 配置 DeviceTrust 后，签到、红包开始、提现申请必须提供与账号和场景匹配的已校验事件。业务入账/扣账与事件消费同一 SQLite 事务；重试返回已有业务操作。红包入账继续要求穿山甲奖励回调确认，并校验其原始设备事件。
- 平台使用 `enforce` 和强制业务请求摘要绑定。普通红包先由服务端报价并锁定金额；挑战包含由服务端规范化的账号、接口、参数、币种、收款对象及报价等完整业务摘要，执行前再对真实请求计算摘要并取得授权。
- Rust Guard 校验应用、哈希事件号、操作号、请求摘要、enforce 模式、私有 permit 及到期时间，网络请求放在数据库写事务之外，事务内再次核验并按操作号防重。permit token 和应用密钥不进入客户端或管理接口 DTO。
- `verify → 待核查`、`hold → 受限` 的本地处置、人工理由和审计继续保留；后台放行对应事件会同步平台审批，不能以本地清除状态代替执行授权。
- 已提交业务与回执记录同事务。随后直接异步发送执行回执；失败保留错误与次数，可通过管理 API 按原事件补报，不重新执行业务。奖励会话开始时锁住金额，确认广告并入账后记录成功回执。当前提现仍为模拟付款，回执不代表真实支付渠道已打款。
- 缺失报告、采集失败、平台不可用分别记录，不伪造设备证据。网页可登录查看资料，收益操作引导最新版 App。
- 挑战的 `hardwareRequired=false` 使用普通 Keystore 签名，不请求硬件证明证书；硬件模式按服务端策略单独验证，失败不降级。当前应用的硬件证明保持关闭，`signature_only` 仅表示持钥签名。
- 平台返回已登记的不透明 deviceId，服务端根据已验签 keyId 关联并保留旧设备的首次见到时间和跨账号完成/在途记录。它不作为客户端通行证，也不代表永久跨重装的物理设备 ID。
- Nginx 覆盖真实 IP，并向本机业务端传专用代理认证头。业务端仅同时满足回环来源与私密代理头校验时采用真实 IP；代理口令不写日志。

具体协议以 `docs/API.md` 和本节为准。实际 Android 网络、硬件证明及真实广告投放仍需目标设备验收。

## 先处置、本地留痕、随后回传

用户要求的“先斩后奏”落实为：明确风险命中后执行当前场景配置的限制，业务状态与本地审计一起提交；随后并发回传平台及更新预警。普通行为先记录，证据不足时归入观察或待核查状态。

资金相关动作使用可追溯的暂缓、核查或限制状态。用户可见金额、奖励及提现处理状态保持准确。规则阈值和限制力度通过后台配置、版本化及验证后启用。

DeviceTrust enforce 模式需要执行授权时，Rust 服务端先按协议取得授权，再提交获准业务。对命中 verify/hold 的请求执行本地暂缓并记录，人工放行后通过既有授权/回执流程继续。SDK 或平台不可用单独记为 assessment_error，按场景策略处理。

平台回传放在 SQLite 事务之外。每条记录包含回传状态、最近失败时间与原始上游错误，可按稳定事件号补传。单条失败只影响该条；业务账本及处置效果使用稳定事件号防重。

## 业务接入点

| 场景 | 稳定关联与落点 |
| --- | --- |
| 注册、登录 | 登录会话或认证会话、最终 user_id；账号/邀请/会话与审计一起提交，失败尝试单独记录 |
| 网页邀请预绑定 | 公开 H5 请求上下文；与 Android SDK 证明分开，关联后续注册账号 |
| 手动或自动绑定邀请 | 统一覆盖 bind_relation、consume_pending，记录首次归属及拒绝原因 |
| 红包开始 | reward_session_id、业务 eventId、账号、设备 keyId/reportId |
| 穿山甲回调 | 保留平台签名、防重和归属验证，引用此前奖励会话的设备证据 |
| 金币入账、签到 | 首次提交前执行策略，完成标记、账本、余额、审计同事务；重复请求沿用原结果 |
| 提现申请和处理 | withdrawal_id、operationId、金额、原状态、新状态、执行主体及回执；补齐跨请求幂等后接真实支付 |

设备报告按 DeviceTrust 的一次性挑战与业务上下文绑定。Rust 认证账号并生成稳定 eventId，SDK 提交 DTP4 加密签名报告，Rust 再调用业务评估、执行授权与回执接口。账号使用内部代号；客户端自报账号、IP 和设备标识作为原始线索留存其可信状态。

原始客户端 IP 根据本服务的可信 Nginx 链确认。代理地址与真实终端地址分开记录。

## 用户端与后台分层

用户端示例文案按实际处置状态使用：

- 参与受限：“当前账户暂不能参与此活动。”
- 提现暂缓：“提现申请正在核查中。”
- 技术故障：“服务暂不可用，请稍后再试。”

公共 JSON、SSE、通知和发布版客户端日志仅保留必要的业务状态与随机追踪号。规则 ID、命中条件、风险分数、模型版本、设备关联、原始平台响应与堆栈只进入后台权限范围。正常开发和构建错误继续直接显示原始原因。

后台需提供：

1. **预警**：严重程度、场景、用户、事件时间、处理状态，能够定位具体事件。
2. **明细**：设备/账号关联、报告与证据引用、信号采集状态、规则与模型版本、原始失败信息。
3. **行为时间线**：注册、登录、邀请、广告会话、奖励、提现等按追踪号串联。
4. **处置记录**：策略建议、实际动作、执行结果、关联账本、平台回执及失败状态。
5. **人工审计**：复核、放行、拒绝、策略调整和导出，记录操作者、时间、理由及前后状态。

审计正文保留必要证据，密码、验证码、访问令牌及私有密钥单独受保护。访问权限、脱敏和留存周期在接入时配置。大厅内存消息与风控审计分别管理。

## 接入验收

- 后台规则明细及证据接口仅管理员可访问，普通账号与公共错误响应中不含这些字段。
- 明确命中时业务限制与本地审计同时存在；平台回执失败有可查询状态。
- 同事件重试不重复发币、扣款或执行处置；回执可以按原事件补报。
- 未授权、不可用、采集失败与已验证风险状态分别呈现给后台。
- 复核放行/拒绝及策略变更均可追溯。
- 同步 SDK 清单、隐私说明与权限声明，再完成真机、误判与真实业务联调验收。

该 SDK 当前交付中的硬件证明尚待真机验收、规则仍待校准；接入完成与处置准确率分别验证。
